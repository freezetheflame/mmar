# MMAR 架构迭代与最终检查

日期：2026-10-10。评审对象：用户 v0.1 Draft；最终建议：[v0.4 设计稿](../mmar-v0.4-design.md)。

## 1. 用户要求与工作范围

要求：继续评审架构，尽可能让 Agent 本身轻量化，先自行做多版迭代，再交付收敛结果。

此次没有实现 Runtime，也没有运行模型费用测试。设计评审的完成标准是：有实际中间稿、有完整最终建议、原能力覆盖明确、关键状态和失败语义可供实现、有可执行的后续验收要求。不能用文档检查代替实现正确性证据。

## 2. 三轮迭代

| 版本 | 本轮工作 | 发现并进入下一轮的问题 |
|---|---|---|
| [v0.1 原文](mmar-v0.1-source.md) | 保留用户输入，作为比较基线 | 目录、消息消费、跨介质提交、多会话和控制语义未固定 |
| [v0.2 草稿](mmar-v0.2-draft.md) | 移除每 Agent 的队列、锁、Task、Adapter，合并共享职责 | 仅移动职责未解决恢复、去重和预算边界 |
| [v0.3 草稿](mmar-v0.3-draft.md) | 统一 Store 真源、定义 claim/commit、恢复和停止屏障 | ready 双真源、每 Agent 等待任务、暂停死等、隐含重试、冗余 generation |
| [v0.4 建议](../mmar-v0.4-design.md) | 删除冗余设施，完整规定目录、投递、控制、恢复与 API | 将实现测试、性能和提供方行为留为明确验收事项 |

第三轮交叉检查还修正了：文本历史版本的保存方式、累计投递预算的提交计数、DRAINING 的接入语义、总预算与每轮输出限制的区别，以及 retired ID 的重复注册行为。

## 4. 轻量化检查

| 检查项 | 设计证据 | 判断 |
|---|---|---|
| 不按 N 创建常驻 Task | 第 4、8、17 节 | 满足设计要求；任务数实测仍待实现 |
| 不按 N 创建 Queue 与 Lock | Store 投递记录、active 映射 | 满足 |
| 不按 N 创建模型客户端 | 共享 DecisionEngine 和 Adapter | 满足 |
| 不按 N 保留完整历史与文本缓存 | 按需文本、有界共享缓存、Store 历史 | 满足 |
| Agent 不负责提交与重试 | claim/reserve/commit 全部由 Runtime | 满足 |
| 简化行动协议 | send、broadcast、空 actions、memory_replace | 满足 |
| 避免过早插件系统 | 只保留 ModelAdapter 和环境 API | 满足 |
| 不为可靠性引入独立服务 | 单 SQLite、固定 worker、无独立 Bus/outbox | 满足 |
| 明确 Runtime 并非零开销 | 第 11、17 节讨论共享线程、Store 串行和测量 | 满足 |

## 5. 反例与失败场景推演

推演方式：对比输入状态、step 状态、预算、控制屏障和输出事务，检查每种事件顺序是否有明确结果。以下不是故障注入测试结果。

| # | 反例或竞争 | v0.4 的预期结果 | 对应约束 |
|---|---|---|---|
| 1 | 记忆已改，输出消息写入失败 | 同事务回滚，记忆不单独更新 | 第 9、10 节 |

| 5 | active 释放时恰好收到消息 | Store 真源重新查询，不依赖单次唤醒 | 第 8 节 |
| 6 | 同 Agent 两个 session 同时有输入 | 跨 session 串行，不混批 | 第 5、8 节 |

| 8 | 一次广播展开到大量接收者 | 验证实际 Delivery 数，超限整轮失败 | 第 7、12 节 |

| 13 | 暂停后当前任务等待提交 | pause 只屏蔽领取，当前任务能提交 | 第 13 节 |

## 6. 明确保留的限制

- 无输入不会自行唤醒；主动联系是被激活后的目标选择。
- 完整目录受上下文预算约束；大量注册不等于所有人一次互相可见。
- 同 ID 的记忆跨 session 共享；会话不是隐私隔离层。
- Markdown 导出有延迟；编辑需显式导入，不能假定运行中改文件立即生效。
- all-or-nothing 使单目标容量不足影响整轮；这是可解释性和简单性的取舍。
- 远端模型请求及费用无法 exactly-once；unknown usage 明确呈现。
- Store 串行写入可能成为瓶颈；需测量，不能预先宣称高吞吐。
- 任意不合作 Adapter 不能保证在指定时间内取消；API 必须暴露未完成清理。

## 7. 外部依据与完成判断

关键可靠性依据采用 SQLite 原子提交、synchronous 配置和 Python asyncio 取消 / TaskGroup 官方文档，链接位于最终建议稿相应段落。上述资料支持技术约束，不替代本系统实现的故障测试。

最终检查确认：用户要求的多轮评审已有可查阅中间稿；Agent 的最小职责与共享基础设施边界明确；原 MVP 能力逐项覆盖；30 个反例均有定义好的预期；需要实现验证的部分没有被宣称为已通过。

结论：架构评审可以交付，建议以 v0.4 为实现基线。运行时正确性、真实成本和规模验收仍属于后续实现阶段，本次没有用文档存在或格式检查冒充这些证据。
