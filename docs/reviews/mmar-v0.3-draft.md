# MMAR v0.3 — 第二轮：补齐可靠执行契约

日期：2026-10-10。基于 v0.2 中列出的缺口。本稿是评审中间版本，不作为实现规格。

## 本轮选择

1. SQLite 保存可恢复的权威状态：记忆正文、输入投递、执行结果、输出消息、事件和预算。
2. `memory.md` 是初始化输入与可重新生成的导出视图，不参与跨介质原子提交。
3. 每次 step 只领取同一 Agent、同一 session 的输入；同一个 Agent 跨 session 也串行。
4. 输入状态为 pending / claimed / consumed / failed / cancelled。
5. 领取输入时持久化 step；模型完成后，在一个事务里提交记忆、输出、输入消费和完成事件。
6. 从 committed step 重试提交时返回既有结果，不再发送消息。
7. 恢复时区分已提交 step 和中断 step；远端模型请求不承诺只执行一次。
8. 会话提供参与者 ID 与允许发言的群组目录，所有输出继承当前 session。
9. 广播在提交时展开为实际收件人，按实际 delivery 数校验预算与容量。
10. 会话 epoch 和 Agent generation 阻止停止、注销后的旧结果提交。
11. 事件在事务里落盘，订阅器在事务外读取事件游标。

## 对候选设计的反例检查

| 场景 | 推演结果 | 进入下一轮的修正 |
|---|---|---|
| 暂停时冻结提交，同时等待当前任务完成 | 当前任务等待提交，pause 又等待任务退出，形成互相等待 | pause 停止领取，允许当前 step 完成，达到静止后才返回 |
| 使用只会增长的内存 ready 队列，重启后重建 | ready、pending 和历史标志出现多个来源，易漏唤醒 | ready 只是有界查询缓存，DB pending 是真源 |
| 每个待执行 Agent 先创建 Task，再等 semaphore | 注册 Agent 多时积累大量等待任务 | 只有取得执行槽位后才创建 step Task |
| 预算在模型返回后扣除 | 多个并发调用都可能通过旧剩余额度 | 调用前事务性预留，不退款；失败和修复也计数 |
| 自动重跑所有崩溃时的 claimed 输入 | 持续崩溃造成无限重跑和不可控模型费用 | step 重启恢复次数有上限，所有请求计入持久预算 |
| 群组成员在模型执行期间变化 | 模型所见目录过期，原收件列表可能已失效 | 提交时重新校验并记录实际展开结果 |
| 一个 Agent 的模型错误逃出 TaskGroup | 其他 Agent 的正常推理也被取消 | 已知错误转换成 step 失败；基础设施故障才终止 Runtime |
| 每轮同步等待 Markdown 导出 | 导出失败把已提交 step 误报为未提交 | 导出独立进行；失败只改变导出状态 |
| 完整身份和记忆永久驻留注册表 | 大量闲置 Agent 仍有显著文本内存 | 注册表只保留小元数据，文本按需加载、有界缓存 |
| 无限可靠回调队列 | 慢消费者使内存持续增长 | 事件游标与有界队列；订阅故障不反向重试 step |

## 本轮仍需收敛的复杂度

- 不需要给每个 Agent 放一个锁；一个 Runtime 拥有 active 集合即可。
- 不需要分布式租约；限定一个 Store 由一个 Runtime 实例拥有。
- 不需要独立 outbox 表；同一 SQLite 中已提交的 delivery 就是持久收件箱。
- 不需要为记忆、路由、调度各建立可插拔框架；先保留 ModelAdapter 和环境接口。
- 不需要自动目录检索工具；MVP 提供预算内完整的会话通信目录。
- 不需要宣称 token 或资金预算绝对准确；调用次数和投递次数先作为严格计数边界。

## 第二轮结论

可靠性需要少量执行元数据，但这些属于共享 Runtime。第三轮将删除候选中的冗余设施，固定生命周期、重试、恢复和 API 的语义，形成最终建议稿。
